# Конспект к защите

Это не «шпаргалка, чтобы выучить». Это карта кода и ответов, чтобы ты мог
открыть любой файл и объяснить, почему он такой.

## 1. Пич на 60 секунд

«Мини-трекер экспериментов: проект → API-ключи → run'ы → батчи метрик.
Postgres — единственный источник истины и одновременно журнал событий. SSE-поток
— это хвост журнала, а не отдельный источник данных: его можно потерять,
продублировать или оборвать, клиент всё равно сойдётся, потому что применяет
события идемпотентно по `seq` и добирает пропуски по курсору. Изоляция — это
`project_id`, взятый из креденла и подставленный в каждый запрос; чужой run
неотличим от несуществующего — оба 404.»

## 2. Пять инвариантов (выучить)

1. БД — единственный источник истины; UI не выдумывает данные.
2. `seq` на run непрерывен, порядок коммитов = порядок `seq`.
3. `unique(run_id, event_id)` — повтор не создаёт строк.
4. Батч — одна транзакция: всё или ничего.
5. Каждый запрос ограничен `project_id` из креденла.

## 3. Вопросы, которые почти наверняка зададут

**Один батч отправили 5 раз. Что будет?**
Первые вставки создадут строки, остальные упрутся в `unique(run_id, event_id)` и
не создадут ничего. Ответ: `accepted=0, duplicates=N`, `last_seq` не меняется.
Строк в БД — по одной на событие. В коде: `src/ingest.ts`, шаги 2–3.

**Пришли 1, 3, 2. Что в БД и что на экране?**
`seq` присваивается по приходу: 1, 2, 3. В строках `ts` остаются 1, 3, 2.
На графике сортировка по `(ts, seq)` → 1, 2, 3. «Последнее значение» — по
максимальному `(ts, seq)`, а не по максимальному `seq`. Курсор и догон — по `seq`.

**Клиент был offline 30 секунд. Что он увидит?**
`EventSource` сам переподключится и пришлёт `Last-Event-ID`. Сервер дочитает из
БД `seq > cursor` и отдаст пропущенное. Если курсор клиента уже больше (он успел
сходить за снапшотом), дубликаты отбросятся по `seq`. Максимальная задержка —
интервал опроса (300 мс), а не 30 секунд.

**Почему SSE, а не WebSocket?**
Нам нужно только server → client. У SSE из коробки реконнект и `Last-Event-ID`,
это обычный HTTP (прокси, cookie, один origin). WebSocket добавил бы ручной
реконнект, ручной replay и двунаправленность, которая не нужна. См.
`src/routes/stream.ts`, `web/src/runStore.ts`.

**Соединение умерло после коммита, но до отправки. Событие потеряно?**
Нет. Строка уже в БД; при следующем коннекте сервер отдаст её по курсору. Ничего
не зависит от доставки в памяти процесса — это главный принцип.

**Почему A не может подписаться на поток B?**
`project_id` берётся из сессии, а не из URL. Перед первым байтом потока
выполняется `select id from runs where id=$1 and project_id=$2`; нет строки —
404, и ни одного `event:` не уходит. `src/routes/stream.ts`.

**Кто-то угадал ID run'а B. Что он увидит?**
404 с телом `{"error":"not_found"}` — ровно как для несуществующего. Проверка
идёт в том же запросе, что и выборка, поэтому нет ни «сначала нашли, потом
проверили», ни оракула существования.

**Почему 404, а не 403?**
403 подтверждает, что объект существует. Для чужого и несуществующего ответ
обязан быть неотличим, иначе API становится справочником чужих ID.

**Почему нельзя полагаться на «UUID трудно угадать»?**
UUID утекают через логи, скриншоты, referer, ответы API. Авторизация должна
работать при известном ID; UUID — не мера безопасности.

**В кэше оказались данные другого проекта. Что будет?**
Ключ кэша — `project_id`, авторизация выполняется до обращения к кэшу, а payload
несёт свой `project_id` и перепроверяется при чтении. Чужая запись не будет
прочитана. TTL 2 с, кэш на процесс; корректность от него не зависит.
`src/cache/runList.ts`.

**Как вы узнали, что событие не потерялось?**
Три уровня: (1) E2E сравнивает множество событий из SQL с тем, что применил
клиент, и с атрибутами DOM; (2) курсор двигается только по непрерывным `seq`, а
дыра вызывает доган; (3) нагрузочный тест: `accepted` всегда равен числу строк в
БД (15000 = 15000, 0 потерь).

**Что ваш E2E НЕ доказывает?**
Другие interleaving'и; надёжность транспорта; корректность при нескольких
инстансах API; отрисовку за пределами проверенных узлов; производительность;
защиту от целенаправленной атаки; durability при падении машины; и то, что сама
спецификация проекции верна — клиент и SQL-оракул могли одинаково ошибиться.

**Где дизайн слабее всего?**
Просмотр (viewer side) не измерен: 50 открытых потоков, каждый опрашивает БД
каждые 300 мс, — это `O(viewers)` запросов. Медленного клиента проверял чтением
кода, а не тестом. Один инстанс API и один Postgres — нет резервирования.

**Что менять первым при 10× трафике?**
Батчинг на клиенте уже есть; дальше — один tailer на run (или `LISTEN/NOTIFY`
как оптимизация с poll-fallback), затем downsample/снапшоты для страницы run,
потом реплики на чтение. Для нескольких инстансов — общий лог (Redis Streams)
или осознанно принять `O(instances)` опрос.

**Что происходит при ротации ключа?**
В одной транзакции все активные ключи проекта получают `revoked_at`, создаётся
новый. Сессии привязаны к ключу через `api_key_id`, а `resolveSession` джойнит
`api_keys.revoked_at` — поэтому сессии, выпущенные старым ключом, умирают
мгновенно. Старый ключ → 401, новый → 200.

**Почему `seq`, а не `ts`, для курсора?**
`ts` — клиентские часы: могут совпадать, идти назад, врать. `seq` — серверный
тотальный порядок, выданный под блокировкой; только он даёт непрерывность и
безопасный догон. `ts` остаётся для отображения.

**Почему не Redis/Kafka?**
БД уже является журналом и источником истины. Брокер добавил бы второй источник
и новый класс отказа (pub/sub теряет сообщения при отключённом подписчике).
На 500 событий/с это не нужно. Redis Streams понадобились бы только для fan-out
между инстансами.

**Сколько стоит `FOR UPDATE`?**
Сериализует писателей **одного** run'а, разные run'ы пишут параллельно.
10 событий/с на run — ничто; на сотнях/с на run понадобится батчинг/партиции.
Измерено: 500 событий/с суммарно, p95 89 мс.

**Клиентские часы врут. Что будет?**
`ts` принимается как доменное время, `received_at` пишется для аудита. Кривая
точка встанет на своё место по `ts`; «последнее значение» считается по
`(ts, seq)`. Мы это не «исправляем», но расхождение видно.

**Почему страница грузит всю историю?**
Для демо-масштаба это честно и просто; при 10^5 событиях нужен downsample и
снапшоты. Это записано в ограничениях, а не спрятано.

**Что с частичной записью?**
Батч — одна транзакция. Тест с инъекцией ошибки: одно событие нарушает CHECK,
в БД ноль строк. `tests/ingest.test.ts`.

**Почему `last_seq` — это max(seq), а не количество?**
При повторном батче `accepted=0`, но `last_seq` должен остаться прежним, иначе
клиент решит, что данных нет. И `last_seq` — это конец снапшота, а не размер
батча.

**Почему нет таблицы батчей?**
Идемпотентность нужна на уровне события; `event_id` — ключ ровно той
гранулярности. Таблица батчей дублировала бы её и добавляла второй срок жизни.

**Почему ключи и токены только хэшами?**
Дамп БД не должен давать живые креденлы. Для 32 случайных байт SHA-256
достаточно: перебирать нечего, bcrypt только замедлил бы каждый запрос.

**Почему cookie, а не Authorization для SSE?**
Браузерный `EventSource` не умеет задавать заголовки. Ключ в query-строке
попал бы в логи. Поэтому ключ один раз меняется на HttpOnly-cookie.

**Почему `SameSite=Lax` и нет `Secure`?**
Lax закрывает cross-site POST. `Secure` выключен, потому что демо идёт по
http://localhost; в проде за TLS его нужно включить — это записано в
ограничениях.

## 4. Порядок разбора кода

1. `src/db/schema.sql` — какие ограничения и почему.
2. `src/ingest.ts` — транзакция, лок, дедуп, `seq`.
3. `src/routes/stream.ts` — хвост журнала, `Last-Event-ID`, backpressure.
4. `web/src/runStore.ts` — fold, курсор, догон, статусы.
5. Тесты: `tests/ingest.test.ts` → `tests/api.test.ts` → `tests/stream.test.ts`.
6. `e2e/tests/consistency.spec.ts` — сценарий с обрывом.
7. `scripts/load.mjs` — откуда цифры.

## 5. Цифры, которые надо помнить

- 25 backend-тестов, 2 E2E.
- 50 runs × 10 events/s, batch 5: 15000 событий, 3000 запросов, p50 58 мс,
  p95 89 мс, p99 177 мс, 0 ошибок, 0 потерь.
- batch 1: 5000/5000, p95 129 мс — батчинг режет число запросов в 5 раз.
- poll 300 мс, heartbeat 15 с, TTL кэша 2 с, лимит 500 событий / 1 MiB,
  сессия 12 ч.

## 6. Честные слабые места (говорить самому)

- Viewer-side нагрузка не измерена.
- Медленный клиент проверен рассуждением, не тестом.
- Один инстанс, нет HA.
- E2E — один сценарий.
- Нет rate limiting и аудита авторизации.
